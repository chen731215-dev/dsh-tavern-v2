# [安全·设计] `parseSummaryOutput` 落库前缺少边界净化 —— 唯一能同时盖住「DOM」与「提示词」两条路的位置

> 状态：**已实施（2.7.15）** —— 三条口径已定并落地，见下方「已定口径」。
> 记录于 2026-10-08。**留档目的**：这条只在聊天记录里出现过，容易丢。
> 议题来源：issue #14 的复核讨论（`PR13-评估与处置建议.md`）。

---

## 一句话

模型输出经 `parseSummaryOutput` 落库后，会被**两个完全不同的消费者**读取：
客户端 `innerHTML`（DOM 路）与系统提示词（提示词路）。
今天这两条路**各自在消费点防守**（渲染层 `esc()` + 2.7.9 的结构化棘轮），
而**数据本身从来没有被净化过**。在落库前净化一处，可以同时盖住两条路。

---

## 实测现状（2026-10-08，基于 2.7.10）

### 数据流
```
最近 N 条对话 → buildSummaryPrompt → callLLM → 模型输出 JSON
                                                  ↓
                                        parseSummaryOutput(text, sessionId)
                                                  ↓
                                  落库：memory.md（summary 正文）
                                        relations.json（relations[] 字段）
                    ┌─────────────────────────────┴─────────────────────────────┐
                    ↓                                                           ↓
        ① DOM 路：客户端 innerHTML                            ② 提示词路：系统提示
        relations[].label / source / target                     summary + 记忆正文
```

### ① DOM 路：已在**渲染层**修好，但那是"每个消费点各自防"
- 2.6.1 把 `esc()` 补成 5 字符（`& < > " '`），关系网三处 tooltip 与世界书 textarea 全量转义。
- 2.7.9 加了**不看变量名**的结构化棘轮（`tools/check-innerhtml-escape.mjs`），
  防止"新建渲染路径 / 合并渲染函数 / 抽统一拼装 helper"时漏掉某一路。
- **但它防的是"渲染层漏转义"，不防"数据本身脏"。** 未来新增任何一个直接消费 `relations[]`
  的地方（导出、通知、第三方面板、文本渲染），都得自己再防一次。

### ② 提示词路：**没有任何针对注入的净化**
```js
// lib/index.js  L3802-3810（summaryText）
const mem = readSessionMemory(sid) || ''
const summaryMatches = mem.match(/# 记忆总结[\s\S]*?(?=\n# |\n> \[|$)/g)
summaryText = '【📝 对话历史总结（AI 请优先参考此总结，忽略之前的完整对话历史）】\n' + summaries + '\n\n'

// lib/index.js  L3861-3864（memoryText）
memoryText = '\n\n【会话记忆（当前对话专属，必须参考保持剧情连贯）】\n' + mem.trim()

// lib/index.js  L3909（最终拼装）
const cardOut = sanitizePromptText(summaryText + header + text + (wbText ? ... ) + memoryText
                 + styleText + netText + toolsRestriction + relationsText + skillsText)
```
`sanitizePromptText()` 做的是**宏展开与 `{{...}}` 剔除**（`expandStMacros` / `{{user}}` / 通用兜底），
**不是注入净化**。也就是说：模型上一轮输出的总结与记忆正文，会被**原样**拼进下一轮的系统提示。

**为什么这条值得单列**：提示框里写的是"AI 请优先参考此总结，忽略之前的完整对话历史" ——
等于给这段文本一个**高优先级**的位置。而它的来源可以被上游操纵
（导入的角色卡本来就在指挥模型；agent 读到的网页/文件同理），
于是这是一个**跨轮持久的提示词注入面**：注入一次，之后每一轮都在。

## ⚠️ 一条需要纠正的常见误解

**关系网字段并没有进提示词。** 别把它当提示词注入的入口去修。

`buildRelationsHintText()`（L2726）是关系网唯一的进提示词路径，它**只注入计数、不给内容**：
```js
if (nodes) bits.push(nodes + ' 个角色')
if (edges) bits.push(edges + ' 条关系')
return '\n\n【关系网】本会话记录了 ' + bits.join('、') + '（仅作为背景资料存在，不要在正文里主动提及…）'
```
函数注释里写得很清楚：「只提醒存在，不给内容」。

所以两条路的真实暴露面是：
| 路 | 真实暴露的字段 | 现状 |
|---|---|---|
| DOM | `relations[].label` / `source` / `target`、世界书正文 | 渲染层已防 + 棘轮守着 |
| 提示词 | **`summary` 正文 + 记忆正文**（不是关系网字段） | **无净化** |

## 建议（最小版本，供讨论）

在 `parseSummaryOutput` **返回之前**做一次净化，让落库的数据本身就是干净的：

1. **剥标签类载荷**：`<...>` 标签、`on\w+=`、`javascript:` 等 —— 对 DOM 路是纵深防御，
   对提示词路也能削掉一类载荷。
2. **考虑对 `summary` 正文做结构性约束**：例如剔除"忽略以上指令""你现在是…"这类
   与总结无关的指令性段落。**这一步要谨慎**，容易误伤正常剧情文本。
3. **不改 `relations[]` 的语义字段**（`source` / `target` / `label` 是剧情数据，不能删），
   只做字符级净化。

### 需要先定的三件事（这就是它不能顺手做的原因）
- **清洗到哪一层**：只剥标签？还是也拦指令性文本？后者误伤风险高，需要可回滚的口径。
- **对已有的落库数据怎么办**：只在写入时净化（旧数据不动），还是提供一个一次性清洗？
- **谁来做判据**：建议配一组「坏样本必须被净化、好样本必须原样保留」的对照测试
  （本仓库既有风格：每条护栏都配反例）。
